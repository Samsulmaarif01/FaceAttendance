# AGENTS.md

Compact operating notes for this repo. See `CLAUDE.md` for the design vision and `docs/system_design.md` for full architecture. Several README/CLAUDE.md instructions are aspirational and do not match the code yet — trust this file and the code.

## Reality check (read before editing)

- This is a **Phase 1 skeleton with Phase 2/3/4/5/6 additions**. `src/camera`, `src/detection`, `src/recognition`, `src/liveness`, `src/database`, `src/pipeline` contain the running pipeline; `src/security` has `keystore.py`, `audit.py`, `tls.py`; `src/sync` has `crdt.py`, `backoff.py`, `compression.py`, `queue.py`, `signing.py`, `sync_manager.py`; `src/index` has `vector_index.py`, `hierarchical.py`, `sharding.py`, `management.py`, `matcher.py`; `src/api` has `app.py` (FastAPI factory `create_app`) + `schemas.py`. `src/dashboard` is a **VeriFace AI kiosk UI** (`index.html` + `static/app.js` + `static/style.css`, plain HTML/CSS/JS, no build, **no CDN** — icons are an inline SVG sprite, fonts are system stacks). It has 4 client-side sections (`presensi`, `riwayat`, `karyawan`, `pengaturan`) toggled by `[data-section]`; keep DOM ids in sync with `app.js` (`$("id")`). It also has a **dark/light theme toggle** (`#btn-theme`) that sets `.light` on `<html>` and persists to `localStorage` (`vf-theme`); light tokens live in the `html.light { … }` block at the end of `style.css` (the camera `.stage` intentionally stays dark). Sync is network-agnostic: `SyncQueue` is **CRDT-backed** (LWW-Element-Set), uploads are **zstd-compressed delta payloads signed with Ed25519**, but no real mTLS socket is wired (transport is injected; `NullTransport` models "offline"). `Database` takes an optional `sync_queue` and enqueues enrollment/template/delete events; `FacePipeline` builds the queue before the DB and injects it. **`faiss`/`hnswlib`/`sklearn` are NOT installed** — `src/index` falls back to a numpy `BruteForceIndex` and a numpy-SVD `PCAReducer` (FAISS backend is lazy/optional; `PipelineConfig.matcher_backend` defaults to `"linear"`).
- `config/default.yaml` / `config/local.yaml` are **not loaded anywhere**. `pipeline.py` never imports `yaml`; all runtime config comes from the `PipelineConfig` dataclass in `src/pipeline/pipeline.py`. Editing YAML has no effect today.
- `models/` is empty and gitignored, but a small **YuNet ONNX** is vendored at `src/detection/data/face_detection_yunet_2023mar.onnx` (Apache-2.0, OpenCV Zoo) — it is the model-free detection fallback. `FacePipeline.__init__` raises `RuntimeError("No recognition models loaded")` when no recognition model loads **unless `PipelineConfig.demo_mode=True`**, in which case `SyntheticEmbeddingModel` is used (see `create_demo_config()`). So `python main.py` (production) fails, but `python main.py --demo` / `--web --demo` work; `--test` is an alias for demo. `test_pipeline_creation.py` still asserts the RuntimeError.
- Detection backends (`PipelineConfig.detector_backend`): `"auto"` (SCRFD if the model loads, else YuNet, else dummy) is the default; `"scrfd"`, `"yunet"`, `"dummy"` force one. `_detect()` returns `[]` from SCRFD errors, uses `YuNetFaceDetector` (`src/detection/yunet.py`, via `cv2.FaceDetectorYN`, needs no extra dep) when available, and falls back to `_dummy_detection` (fixed centered box) only if both fail. **YuNet cost scales linearly with frame pixels** (1080p ≈ 220 ms vs 640×480 ≈ 20 ms), so it detects on an image scaled to fit `PipelineConfig.detection_working_size` (default `(640, 480)`, aspect ratio preserved, never upscaled) and maps boxes/landmarks back to original coordinates; the dashboard also requests 640×480 from `getUserMedia` to keep the JPEG payload small. Note: **OpenCV 5.0 here has NO `cv2.CascadeClassifier`**. Demo recognition bypasses liveness (`_check_liveness` returns live in demo mode).
- The dashboard live loop (`src/dashboard/static/app.js`) must never overlap itself: `liveLoop()` returns early while `loopBusy` is set, and `refreshAttendance/refreshStats/refreshUsers` run only when the attendance status actually changes (`attendanceChanged`) instead of on every 700 ms frame — a 5 s interval still refreshes as a fallback. **Privacy on the kiosk**: `presentUsers` + `PRESENCE_GRACE_MS` (3 s) is the single definition of "this person has left"; once it fires, `pruneMatchCard()` calls `resetMatchCard()` so the next person never sees the previous person's name, NIK, avatar initials, similarity or attendance time. `resetMatchCard()` also blanks those fields (not just hides `#match-body`) and is called from `clearPresence()` (mode switch, camera start/stop). The transient toast is deliberately **left** to expire on its own — it is the just-scanned person's own feedback, not a cross-person leak.
- `process_frame` **matches**: `FacePipeline._get_user_templates()` delegates to `Database.get_user_templates()`, which returns `user_id -> decrypted embedding`. Embeddings are stored **Fernet-encrypted at rest** in a `users.encrypted_embedding` column (migrated on init); the biohashed template remains the primary record. Demo uses **YuNet detection** (real tracking) and **bypasses liveness** (`_check_liveness` returns live in demo mode).
- Enrollment is **only** for registering a face and never writes attendance. `FacePipeline.enroll_from_frame(frame, user_id, name)` takes `user_id=None` (it invents one only when it really inserts) and matches the new embedding against **all** templates via `Database.get_user_templates(include_inactive=True)`; above `PipelineConfig.enroll_duplicate_threshold` (default 0.60, deliberately stricter than `recognition_threshold`) it refuses instead of creating a second user: same face + same `user_id` → `updated`, same face + soft-deleted owner → `reactivated` (via `Database.reactivate_user`, which restores the row so the old attendance stays linked), otherwise → `duplicate` + `existing_user_id`/`existing_name`/`similarity`. **Order matters here:** the `not owner.is_active` branch is checked *before* the `user_id == owner.id` refresh, so re-enrolling an archived person while typing their old id reactivates them instead of answering `updated` while the row stays `is_active = 0` (which would look like success but never be recognisable). `DELETE /api/users/{id}` is a **soft delete** (`is_active = 0`) and `list_attendance` LEFT JOINs `users` so records of a deleted user keep showing their name.
- **Deleting a user has two modes.** `DELETE /api/users/{id}` (default) = **archive** / soft delete (`is_active = 0`): the template and every attendance record survive, so the face is still recognised as "already registered" and re-enrolling reactivates the same user instead of creating a duplicate; archived users are listed with `GET /api/users?include_archived=true` (flag `is_archived`) and brought back with `POST /api/users/{id}/restore`. `DELETE /api/users/{id}?permanent=true` = **hard delete** (`Database.hard_delete_user`): the user row, its Fernet-encrypted template and all of their attendance rows are removed, so the same face can be enrolled again as a genuinely new user. Responses carry `mode` (`archived`/`permanent`/`restored`) and `attendance_deleted`. The dashboard uses a two-choice dialog (`#dlg`) and a "Tampilkan arsip" checkbox. `list_attendance` LEFT JOINs `users` so records of an archived/deleted user still show their name. **Watch out:** never leave a second `deleteUser`/similar declaration behind in `app.js` — function declarations hoist, so a stale duplicate silently wins. Run `node --check src/dashboard/static/app.js`; the Python suite does not parse the dashboard JS.
- Each user stores an avatar thumbnail (`users.photo` BLOB, JPEG q80 of the face region padded 25 %, written by `FacePipeline.face_thumbnail(frame, detection)`), served by `GET /api/users/{id}/photo` and flagged as `has_photo` in `/api/users`. The dashboard shows it in a **Foto** column of the Daftar Pengguna table and in `#match-avatar-photo` (the card next to the Face ID kiosk), falling back to initials when absent. The old `#enroll-preview` block was removed — the photo belongs in the table and the match card, not above the form. **Photo-only backfill**: `POST /api/users/{id}/photo` (multipart `file`) + the `#i-camera` button on the `Aksi` column let an operator attach/replace the avatar of an **existing** user via `FacePipeline.update_photo_from_frame`, which never rewrites the template and never writes attendance — needed because users enrolled before the column existed have `photo = NULL`. Because the GET has a stable URL with `Cache-Control: max-age=300`, `app.js` keeps a `photoStamp[userId]` and appends `?t=…` after a replacement. The photo is also refreshed on **Daftar ulang** and on **reactivate**: `Database.update_user_embedding(..., photo=None)` / `Database.reactivate_user(..., photo=None)` only overwrite `photo` when bytes are supplied, so refreshing a template never silently wipes an avatar. **Avatar comes from enrollment only**: `process_frame` (the attendance/recognition path) **never** writes `photo` — an attendance frame is *not* the registered photo. `photo` is written only by `enroll_from_frame` (live capture at enrolment, or the uploaded file) and by `update_photo_from_frame` (the manual "Isi / ganti foto" button in the `Aksi` column — also a file upload, never the kiosk camera). A user enrolled before the `photo` column existed therefore keeps showing initials until an operator uploads a photo or re-enrols; do **not** re-add an auto-capture from a recognition frame (`test_recognition_never_fills_in_a_missing_photo` / `..._never_overwrites_an_existing_photo` guard this). `#match-avatar-text` (initials) is hidden while `#match-avatar-photo` is shown, and both are reset in `resetMatchCard()`. **Three traps that made the photo look "not implemented"**: (1) the avatar `<img>` must NOT use `loading="lazy"` — the users table lives inside `<section hidden>`, and lazy images in a `display:none` container are not fetched, so the cell rendered as an empty grey circle; `photoCell()` instead carries `data-initials` and `wire()` swaps in initials from a capture-phase `error` listener (`error` on `<img>` does not bubble). (2) `index.html` used to ship without `Cache-Control`, so the browser could serve the stale page, which pins an old `?v=` on `app.js`/`style.css` and makes a code change appear to do nothing; `_mount_dashboard` now adds a middleware setting `no-cache, must-revalidate` on `/` and `/static` only (routes under `/api` keep their own caching, avatars stay `max-age=300`). (3) the kiosk avatar carries **only an `id`** (`<img id="match-avatar-photo">`, no `class`), so it must be styled with an **id selector** — `.match-avatar-photo { position:absolute; inset:0; object-fit:cover; … }` never matched anything, so the raw JPEG rendered at its natural size inside the 88 px card (the table avatar looked fine because `photoCell()` really emits `class="photo-thumb"`). `tests/dashboard/test_dashboard.py` now fails on any CSS class that is never applied and any CSS `#id` absent from `index.html`, so this class of silent no-op cannot come back; bump `?v=` in `index.html` after editing `style.css`/`app.js`.
- Enrollment never touches the attendance kiosk stage. Never set `photo.hidden = false`, never write to `#overlay`, and never call a stage helper from the enrollment path: `liveLoop()` bails out on `!photo.hidden`, so hijacking the kiosk stage silently kills face recognition there. `showPhoto()`/`drawRegisteredLabel()`/`#enroll-preview` were removed for exactly that reason (the kiosk now only ever *hides* `#photo`, from `startCamera`).
- Every enrollment outcome must reach the operator through a **toast**, never only the `#status` line: `hideToast()` wipes any leftover toast at the start of an enroll attempt (otherwise a stale green "Pendaftaran berhasil" from the previous photo makes a failed enroll look saved), and `enrollFailed()` shows a red "Wajah tidak tersimpan" toast. On the scan side, `alertUnknownFaces()` fires a red **"Wajah tidak terdaftar"** toast when faces are detected but none match, deduped by `unknownWarned` and reset when the frame is empty or a match returns.
- `EnsembleExtractor.extract(image, landmarks)` **aligns internally**. The pipeline must pass the **original frame** (not a pre-aligned crop) or embeddings come out zero/garbage.
- Stale references you will not find: `scripts/download_models.py`, `scripts/quantize_model.py`, module `facial_attendance`, `tests/test_face_pipeline.py`.

## Commands

Run everything from the repo root. There is no installed package (`pyproject.toml`/`setup.py`), so `from src...` imports only work with cwd = repo root.

Windows console is `cp1252`: the root test scripts print `✓/✗/✅/❌` and crash with `UnicodeEncodeError` unless you prefix UTF-8. Use `python -X utf8 ...` (or `PYTHONIOENCODING=utf-8`).

```bash
# Hand-rolled test scripts (not pytest). test_pipeline.py is currently red.
python -X utf8 test_imports.py
python -X utf8 test_pipeline.py          # 3 pass / 2 fail (liveness kwarg + no models)
python -X utf8 test_pipeline_creation.py # fails: RuntimeError no recognition models

# Real pytest suites (phase 2 + phase 3 + phase 4 + phase 5 + phase 6). pytest must be installed first.
python -m pytest tests/ -v

# Phase 6 local web UI (no Docker, no ONNX models needed). Serves src/dashboard.
python -X utf8 main.py --web --demo      # http://127.0.0.1:8000
python -X utf8 -m src.api                 # module equivalent (--real for models/…onnx)
```

- `test_pipeline.py` failure 1: it calls `LivenessDetector(min_frames=...)` but the param is `blink_frames`. Failure 2: `FacePipeline` needs loadable recognition models (or `demo_mode`).
- `tests/` has seven populated suites: `tests/recognition/test_accuracy.py` (phase 2) + `tests/recognition/test_synthetic.py` (phase 6), `tests/security/test_security.py` (phase 3), `tests/sync/test_sync.py` (phase 4), `tests/index/test_index.py` (phase 5), `tests/api/test_api.py` (phase 6), `tests/detection/test_yunet.py` (phase 6), and `tests/dashboard/test_dashboard.py` (CSS/markup wiring of the no-build dashboard); other `tests/*` dirs are empty (`__init__.py` only).

## Architecture pointers

- Entry: `main.py` (inserts repo root on `sys.path`, then `from src.pipeline import ...`).
- Orchestrator: `src/pipeline/pipeline.py` → `FacePipeline.process_frame` runs detect → quality gate → align → embed → liveness → match.
- `EnsembleExtractor.extract()` re-aligns internally, so `pipeline.py` must pass the **original frame** to it (it still calls `aligner.align` once for display). Passing a pre-aligned crop with original-coordinate landmarks yields zero embeddings — a real bug that was fixed in phase 6.
- `src/api/app.py` exposes `create_app(config=None, pipeline=None)` (a **factory**, no import-time side effects). Endpoints: `GET /api/health`, `POST /api/recognize` (query `?log=false` to skip attendance, `?direction=in|out`), `POST /api/enroll` (form `name`, optional `user_id`), `GET /api/users` (includes `attendance_count`/`last_attendance`/`checked_in_today`/`checked_out_today`), `DELETE /api/users/{id}`, `GET /api/attendance` (records include `direction`), `DELETE /api/attendance`, `GET /api/stats`, `POST /api/sync`; `/` serves `src/dashboard/index.html` and `/static` the assets. Attendance logging follows an alternating **masuk → pulang → masuk → pulang** sequence within a local day, decided by the user's **most recent** record (`Database.get_today_last_direction`): repeating the current direction is a `duplicate`, `direction="out"` with no earlier `"in"` today is refused (`not_checked_in`), and after a `pulang` the user may check in again. `PipelineConfig.attendance_throttle_seconds` (default 60s) still rate-limits logging, keyed per `user:direction`, and the opposite key is dropped after each successful log so a check-out/check-in transition is never delayed; `FacePipeline.reset_attendance_throttle()` clears this in-memory state when attendance rows are deleted (the API calls it from `DELETE /api/attendance` and `DELETE /api/users/{id}`). The dashboard only re-announces a per-user attendance status when the person actually leaves and re-enters the frame (`presentUsers` + `PRESENCE_GRACE_MS`). `FacePipeline.process_frame(frame, log_attendance=True, direction="in", gate=False)` returns each face with `attendance_status` (`logged` / `duplicate` / `not_checked_in` / `skipped` / `no_match`) and `attendance_logged` so the UI can pop a toast. The `attendance` table has a `direction` column (`'in'`/`'out'`, migrated on init). The dashboard's "Register from image" path is enroll-only (no attendance). **Gate (IoT) mode**: `POST /api/recognize?gate=true` (and `FacePipeline.process_frame(..., gate=True)`, toggled in the dashboard under *Pengaturan → Mode Gate*) relaxes the attendance pairing rule for door access — a recognised + live face always gets `gate_granted: true`, and `direction="out"` is recorded even with no earlier `"in"`, because leaving the building must never be blocked by an attendance rule. In attendance mode a repeated `direction` shows a green "Sudah absen" toast (status `duplicate`), not a warning.
- `src/security/`: `KeyStore` (file/hardware backends), hash-chained `AuditLog`, and mTLS cert/context helpers. `Database` derives its Fernet key via `KeyStore` and records enrollment/verification/attendance events when an `audit_log` is passed; `FacePipeline` wires one via `PipelineConfig.audit_enabled`/`audit_log_path`.
- `.gitignore` excludes `config/local.yaml`, `models/*`, `data/*`, `logs/*`, `certs/*`, and all `*.onnx/*.db/*.pem`.
